# 统一任务 CLI 与控制面评审

## 目标

所有用户通过 `rops job` 提交计算任务。用户只描述任务目的、硬件类别和准确的执行 bundle，
不选择具体集群，也不接触 LTP 的实际任务身份。Orbitree 负责校验、选址、提交和对账。

## 用户契约

```bash
rops job submit /absolute/bundle --work COMMON-0007 --hardware b --kind inference
rops job status LOGICAL_JOB_ID
rops job list
```

提交结果只包含逻辑任务 ID、逻辑状态和请求资源。公共 Schema 不包含集群、LTP 任务名、命令
输出或调度证据。相同用户使用相同幂等键重复提交时，只能得到同一个逻辑任务。

## 内部执行原则

1. 先校验 `config.yaml`、`run.sh`、可选 `train.py` 的绝对路径、内容摘要和准确拓扑。
2. 正式训练必须提供与当前 bundle 一致且仍有效的 preflight receipt。
3. 使用新鲜容量快照选择同硬件资源池。B 卡优先常规池，再选择可容纳任务且余量最大的 Book
   池；没有资源池能立即容纳时，仍选择同硬件候选并提交排队。H100 任务固定进入 H100 池。
4. 提交前记录同用户、同任务基名的现有任务。提交后只接受实时清单中唯一新增的匹配任务，
   再把其实际身份绑定到逻辑任务。
5. LTP 超时、回执缺失、身份候选冲突、进程中断或提交后落库失败都进入 `needs_review`，不得
   自动重投。
6. bundle 在逻辑入队后发生任何变化时拒绝提交，要求使用新的幂等键重新创建请求。
7. 集群和实际任务身份只存放在内部 `ExternalJob` 与调度回执中，不进入用户响应。

## 状态机

```text
accepted -> dispatching -> verifying -> queued -> running
                 |             |
                 +-> failed    +-> needs_review
                 +----------------> needs_review
```

`dispatching` 是内部瞬时状态，对用户仍显示为 `accepted`。服务重启时发现未完成的
`dispatching`，会直接转为 `needs_review`，不会重放可能已经产生外部副作用的命令。

## 显式评审结论

当前实现适合作为受控试用版本：提交入口已经统一，集群选择已从用户界面移除，幂等和不确定
结果处理满足保守执行要求，真实 LTP 提交默认关闭。开启试用前，管理员仍需核对 LTP CLI
身份、共享目录和容量快照来源。

以下缺口不应在试用说明中隐藏：

- 当前 API 使用实例级访问令牌，尚未把令牌与提交人身份可信绑定。正式多用户开放前必须接入
  服务端认证身份，不能继续信任客户端上报的用户名。
- 当前全局快照只覆盖排队和运行任务。任务从清单消失时，系统不会猜测它已经成功完成；终态
  需要后续接入 LTP 详情或产物证据。
- 调度抢占使用单进程锁，适用于当前单控制面实例，不支持多个主动实例同时派发。
- 当前 CLI 只覆盖提交、查询和列表。取消、续跑、扩缩容以及同目的任务的跨集群收敛策略仍需
  通过新的受管动作实现，不能绕过控制面直接补命令。

因此推广顺序应为：先保持 `ROPS_MANAGED_JOB_SUBMIT_ENABLED=false` 验证逻辑接单，再对少量用户
启用真实提交；完成可信身份、终态探针和多实例派发租约后，才将其设为唯一提交入口。
